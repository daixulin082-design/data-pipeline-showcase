# 反爬对抗踩坑清单（15 条）

> 全部来自真实项目，按踩坑频率排序

---

## 1. 把 429 当成「没有下一页」

**现象**：采集中途静默停止，数据量远小于预期。

**原因**：`if not items: break` —— 但 429 返回的也是空 body。

**修复**：
```python
if r.status in (429, 403):
    time.sleep(4 + attempt * 2)
    continue        # 重试，不是 break
```

---

## 2. 用同一套停机条件应对所有站点

**现象**：某些站翻到第 15 页就停，实际有 3,800 页。

**原因**：有的站按时间倒序（新帖插入首页），有的按 id 正序（新帖在末页）。
用「连续 N 页无新数据」的策略，在倒序站上会误判。

**修复**：先取 3 页样本，看 id 的变化方向：
- id 递增 → 按 id 停机
- id 乱序/倒序 → 按日期停机

---

## 3. 每请求新建连接

**现象**：速度慢、TLS 握手占比高、更容易被判定为爬虫。

**修复**：每个线程维护一个 keep-alive 连接（`threading.local()`）。

```python
_tls = threading.local()

def _conn(host):
    c = getattr(_tls, "conn", None)
    if c is None:
        c = http.client.HTTPSConnection(host, timeout=30)
        _tls.conn = c
    return c
```

注意：服务端返回 `Connection: close` 时要重建。

---

## 4. 忽略 `Connection: close` 响应头

**现象**：偶发大量失败，重试就成功。

**原因**：服务端主动关闭了连接，客户端还在往旧连接发请求。

**修复**：
```python
if (r.getheader("Connection") or "").lower() == "close":
    c.close()
    _tls.conn = None
```

---

## 5. 只在内存里攒结果，最后一次性写盘

**现象**：跑了 6 小时，进程被杀，一条数据没留下。

**修复**：每条结果立即 append + flush，配合已采 ID 集合做断点续传。

---

## 6. 用文本相似度去重

**现象**：同一实体的 3 条帖子都留下了，去重率只有 60%。

**原因**：同一实体重复发布时标题和正文都会改写，但联系方式不变。

**修复**：用业务指纹（联系方式组合 + 城市）做去重键。

---

## 7. 用关键词黑名单过滤广告

**现象**：误杀率高（「环境像工作室一样干净」被判为广告）。

**修复**：加权评分。强信号（招聘/加盟）+3，弱信号（工作室/会所）+1，≥4 剔除。

---

## 8. 忽略价格字段的黑话

**现象**：价格字段大量为空或异常。

**原因**：原始文本里的价格写法：
```
消费价格：800        直接数字
3米                  米 = 百元
6P / 8p              P = 百元
3张                  张 = 百元
1200元/次
```

**修复**：多规则优先级匹配 + 乘数换算：

```python
PRICE_RULES = [
    (r"价格[：:]\s*(\d{2,5})", 1),
    (r"(\d{1,2})\s*米", 100),
    (r"(\d{1,2})\s*[pP]", 100),
    (r"(\d{1,2})\s*张", 100),
]
```

---

## 9. 图片地址抓成了页面里的装饰图

**现象**：每条记录关联 11–12 张图，全是站标、广告横幅。

**修复**：限定在正文容器内取图（如 `#viewer img`），并排除 `/template/`、`/static/` 路径。

---

## 10. 前端强缓存导致新数据不显示

**现象**：服务端数据已更新，浏览器还是旧的。

**原因**：`fetch(url, {cache: 'force-cache'})`。

**修复**：构建时生成版本号，URL 带上 `?v=BUILD`，并用 `cache: 'no-cache'`。

---

## 11. 首屏加载全量数据

**现象**：1 万条数据 8 MB，首屏卡 5 秒。

**修复**：按区域/类别分片，首屏只加载第一片，其余后台异步。

---

## 12. 后台加载完成后直接重绘列表

**现象**：用户滚到中间，新数据加载完，页面跳回顶部。

**修复**：检测滚动位置，`window.scrollY > 200` 时只更新计数，不重绘。

---

## 13. 服务端信任客户端 Cookie 字段

**现象**：改 Cookie 里的 `level`/`vip` 就能看到付费内容。

**这是漏洞，不是功能**。如果你的系统这样做，服务端必须从会话取权限。

---

## 14. 用 GET 请求改数据

**现象**：某些站的「解锁」是 GET 请求，刷新页面就重复扣费。

**排查**：抓包时注意 GET 请求是否产生副作用。

---

## 15. 没有做数据量对账

**现象**：以为采了 4 万条，实际只有 1.5 万（限流中断）。

**修复**：列表阶段就统计总数（站方通常在列表接口返回 `total` 字段），
采完后对账：

```python
expect = list_api_total
actual = len(rows)
assert actual >= expect * 0.95, f"数据缺失：{expect} → {actual}"
```
